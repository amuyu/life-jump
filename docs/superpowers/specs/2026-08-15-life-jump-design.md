# Life Jump — 설계 문서

작성일: 2026-08-15

## 1. 개요

땅에서 시작해 하늘을 거쳐 우주까지 끝없이 올라가는 2D 수직 플랫포머 웹 게임.
발판을 밟고 점프해 높이를 쌓고, 도중에 얻은 재화로 옷을 만들고 상승 보조 아이템을
구매해 다음 판을 더 높이 올라간다.

### 핵심 결정 사항

| 항목 | 결정 |
|---|---|
| 진행 구조 | 무한 상승 + 최고기록 경쟁, 재화는 판을 넘어 누적되는 로그라이트 |
| 점프 조작 | 수동 점프 (↑ / Space), 길게 누르면 높게 |
| 낙하 처리 | 에너지 1칸 감소 + 화면 안 최하단 발판에서 부활, 점수·카메라 유지 |
| 상점·옷장 | 게임 밖 로비에서만 접근 |
| 퀴즈 | 일반 상식/재미 퀴즈 (성인 포함), 4지선다 |
| 그래픽 | 픽셀아트, 코드 내장 픽셀맵 데이터 (외부 이미지 파일 0개) |
| 기술 스택 | Vite + TypeScript + Canvas 2D |

### 비목표 (Non-goals)

이번 스펙 범위에 포함하지 않는 것:

- 서버, 계정, 온라인 리더보드 — 저장은 전적으로 localStorage
- 사운드/BGM
- ~~모바일 터치 조작~~ → `2026-08-17-touch-controls-design.md` 에서 해제
- 적, 발사체, 보스
- 다국어 지원 (한국어 전용)

## 2. 기술 스택과 선정 근거

**Vite + TypeScript + Canvas 2D**를 채택한다.

게임 엔진(Phaser)이나 렌더링 라이브러리(PixiJS)를 쓰지 않는 이유는, 이 게임의 물리가
"중력 + 좌우 이동 + 발판 상단 단방향 충돌" 세 가지로 끝나기 때문이다. 실제 복잡도는
메타 시스템(에너지, 아이템 경제, 옷, 상점, 퀴즈, 저장)에 있고 엔진은 그 부분을 돕지
않는다. 화면에 동시 존재하는 스프라이트가 수십~수백 개 수준이라 WebGL이 해결하는
병목도 발생하지 않는다.

렌더링 계층을 게임 로직에서 분리해 설계하므로, 향후 연출 요구가 커지면 PixiJS로의
교체가 `render/` 디렉토리 교체 수준으로 가능하다.

- 번들 목표: 100KB 미만
- 배포: Vite 정적 빌드 → GitHub Pages 또는 Vercel (서버 불필요)
- 테스트: Vitest

## 3. 좌표계와 렌더링 기반

### 논리 해상도

**180 × 320 고정**. 창 크기에 맞춰 가능한 최대 **정수 배율**로 확대하고 남는 공간은
레터박스 처리한다. 픽셀아트가 뭉개지지 않으려면 정수 배율이 필수이며,
`ctx.imageSmoothingEnabled = false`를 설정한다.

### 월드 좌표계

월드 좌표는 **y가 위로 증가**하는 수학 좌표계를 쓴다. 화면에 그릴 때만 변환한다.

```
screenY = LOGICAL_HEIGHT - (worldY - camera.y)
```

`camera.y`는 **화면 하단**의 월드 y다.

**축척: 10px = 1m.** 캐릭터가 16px이므로 키 1.6m에 해당한다.

### 높이를 나타내는 네 가지 값 (혼동 금지)

부활 시 `player.y`는 내려가지만 점수는 내려가면 안 된다. 따라서 네 값을 명확히
분리하고, 각각을 무엇이 소비하는지 못 박는다.

| 값 | 의미 | 단조성 |
|---|---|---|
| `player.y` | 현재 물리 위치 | 오르내림 |
| `run.maxHeight` | **이번 판 최고 도달 높이 = 점수** | 단조 증가 |
| `camera.y` | 화면 하단의 월드 y | 단조 증가 |
| `save.bestHeight` | 역대 최고 기록 | 단조 증가 |

**네 값 모두 픽셀(px) 단위다.** 미터 변환(`/ 10`)은 화면에 표시할 때만 한다.
저장 스키마에 미터를 섞으면 이후 마이그레이션에서 10배 오차가 발생한다.

**각 값의 소비처:**

| 용도 | 사용하는 값 | 이유 |
|---|---|---|
| 점수 표시 / 기록 갱신 | `run.maxHeight` | 부활해도 점수가 깎이면 안 된다 |
| 배경·구간 판정 | `camera.y + 160` (화면 중앙) | 부활 시 배경이 깜빡이지 않는다 |
| 발판 폭·간격 난이도 | **그 발판 자신의 y** | 생성 시점에 결정 → 부활과 무관 |
| 아이템 드랍 배율 | **그 발판 자신의 y** | 위와 같음 |
| 퀴즈 난이도 | **물음표 아이템이 놓인 발판의 y** | 위와 같음 |

생성 시점에 결정되는 것은 전부 "그 발판 자신의 y"를 기준으로 삼는다. 이렇게 하면
플레이어의 오르내림과 무관하게 세계가 결정론적으로 만들어진다.

### 카메라

플레이어가 화면 상단 40% 지점을 넘으면 카메라가 따라 올라간다. 즉
`camera.y >= player.y - LOGICAL_HEIGHT * 0.6` (= `player.y - 192`)을 유지한다.

**카메라는 절대 내려가지 않는다.**

## 4. 물리

### 수치

| 항목 | 값 | 결과 |
|---|---|---|
| 중력 | 1200 px/s² | |
| 점프 초기 속도 | 480 px/s | 최대 점프 높이 96px (9.6m) |
| 점프키 릴리즈 컷오프 | 300 px/s | 최소 점프 높이 37px (3.7m) |
| 좌우 이동 속도 | 90 px/s | 공중에서도 조향 가능 |
| 최대 낙하 속도 | 600 px/s | |

### 가변 점프

점프키를 누르는 순간 `vy = 480`으로 설정한다. 키를 떼는 시점에 상승 중이면
(`vy > 300`) `vy = 300`으로 잘라낸다. 결과적으로 탭하면 3.7m, 끝까지 누르면 9.6m.

발판 간격이 이 범위 안에 배치되므로, "얼마나 오래 누를지"가 매 점프의 판단거리가 된다.

### 고정 타임스텝

물리는 **1/60초 고정 스텝**으로 갱신한다. 렌더 프레임과 분리해 프레임률이 흔들려도
점프 높이가 달라지지 않게 한다. 누적 시간이 여러 스텝을 요구하면 반복 처리한다.

### 밀린 시간 처리 (반드시 지킬 것)

스텝 수만 제한하고 남은 accumulator를 보존하면, 탭을 백그라운드에 두었다 돌아왔을 때
**밀린 시간을 따라잡느라 한동안 슬로모션처럼 동작한다.** 시간을 버려야 한다.

1. **프레임 delta를 100ms로 클램프한다.** 100ms를 넘는 간격은 그 초과분을 버린다.
   1/60초 = 16.67ms이므로 한 프레임 최대 6스텝이다.
2. **한 프레임당 최대 6스텝**을 하드 백스톱으로 둔다. 초과분은 accumulator에
   남기지 않고 폐기한다 (죽음의 나선 방지).
3. **`visibilitychange`로 탭에 복귀할 때 accumulator를 0으로 초기화한다.**

3번은 8절의 퀴즈 모달 종료 시 초기화와 같은 이유이며, 같은 함수를 공유한다.

### 스윕 충돌 (Swept Collision)

최대 낙하 속도 600px/s는 프레임당 10px이고 발판 두께는 6px이다. 단순 AABB 겹침
검사로는 **고속 낙하 시 발판을 관통한다.** 따라서 이전 프레임 위치와 현재 위치
사이를 발판 상단선이 통과했는지 검사한다.

착지 조건 (세 가지 모두 만족):

1. 하강 중 (`vy < 0`)
2. `prevFootY >= platformTop && currFootY < platformTop`
3. x축 구간이 겹침

발판은 **위에서만 착지**하고 아래에서는 통과한다. 발판의 옆면·아랫면 충돌은 구현하지
않는다 — 무한 상승 게임에서 발판에 머리를 박는 것은 스트레스 요인일 뿐이다.

### 좌우 경계

화면 좌우는 **벽으로 막는다**. 화면 순환(wrap)은 수동 점프 방식에서 착지 지점 판단을
혼란스럽게 만든다.

## 5. 발판

### 크기와 간격

높이가 올라갈수록 어려워진다. 최대 점프 높이(96px) 안에 항상 들어오도록 보장한다.

| | 시작 (0m) | 최대 난이도 |
|---|---|---|
| 폭 | 40px | 24px |
| 수직 간격 | 32px | 72px |

### 종류

| 종류 | 등장 구간 | 동작 |
|---|---|---|
| 일반 | 전 구간 | — |
| 스프링 | 전 구간, 드묾 | 점프 속도 480 → 750 (높이 23m) |
| 부서짐 | 하늘부터 | 밟고 0.3초 후 소멸, **3초 후 되살아남** |
| 움직임 | 하늘부터 | 좌우 왕복, 위에 선 캐릭터도 함께 이동 |

#### 부서진 발판이 되살아나는 이유

발판 생성은 **사다리 한 줄**이다 — `generateUpTo`가 배열의 마지막 발판
하나에서만 다음을 잇기 때문에 곁가지가 없고, 모든 발판이 위아래를 잇는
유일한 연결점이다. 20개 시드 · 링크 2,719개를 측정한 결과 부서지는 발판
191개 중 **129개(67.5%)** 가 사라지면 바로 위 발판이 아래에서 도달
불가능해진다. 올라가는 중에는 이미 지나친 뒤라 문제가 없지만, 떨어져
되돌아오면 길이 영구히 끊겨 판이 진행 불가능해진다.

되살아나게 두면 그 막힘이 스스로 풀린다. 되살아난 발판은 타이머가
초기화되어 다시 밟으면 또 부서진다 — 반복 사용은 여전히 불가능하므로
"머무르지 말라"는 긴장은 유지된다. 죽어 있는 동안에는 착지 대상에서
빠지고 그 위의 아이템도 주울 수 없으며, 되살아날 때 함께 돌아온다.
화면에는 되살아나는 정도에 비례해 진해지는 잔상으로 그린다 — 아무것도
보이지 않으면 막힌 플레이어가 기다릴 이유를 알 수 없다.

### 움직이는 발판 파라미터

| 항목 | 값 |
|---|---|
| 이동 속도 | 25 px/s |
| 이동 범위 | 생성 중심 기준 ±20px (총 40px) |
| 궤적 | 등속 왕복 (삼각파). 사인파를 쓰지 않는다 — 등속이 예측 가능해 조작감이 좋다 |
| 초기 위상 | 항상 **중심에서 오른쪽으로 출발** |

### 생성과 재활용

카메라 상단 위로 계속 생성하고, 카메라 하단 아래로 벗어난 발판은 폐기한다.
시야 밖 발판을 메모리에 유지하지 않는다.

### 도달 가능성 불변식

**모든 발판은 직전 발판에서 도달 가능해야 한다.** 기준은 **최소 업그레이드 상태**
(점프 속도 480, 좌우 속도 90)이며, 상점 강화는 여유분으로만 작용한다.

움직이는 발판이 끼면 착지 예상 시점의 위치가 달라지므로, 생성 시점의 수평 거리만
검사해서는 도달 가능성을 보장할 수 없다. 그렇다고 "체공 구간 중 어느 한 시점에
시간별 AABB가 겹치는가"를 검사하려면 점프 궤적 시뮬레이션이 필요하고 위상 오차에
취약해진다.

대신 **더 강한 정적 조건**을 쓴다:

> 출발 발판이 이동형이면 **플레이어에게 가장 불리한 끝**(목표에서 먼 쪽 끝),
> 목표 발판이 이동형이면 역시 **가장 불리한 끝**을 기준으로 삼는다.
> 이 최악 조합에서 도달 가능하면 배치를 승인한다.

최악 위치에서 도달 가능하면 모든 시점에 도달 가능하므로 **검사에서 시간 축이
사라진다.** 실제 궤적보다 보수적이라 일부 유효한 배치를 과하게 거르지만, 도달
불가능한 발판이 생성되는 것보다 낫다. 판정도 테스트도 결정론적이 된다.

구체적 조건 두 가지:

1. 수직 간격 ≤ 최대 점프 높이(96px)에서 안전 여백 8px를 뺀 **88px**
2. 수평 거리 ≤ 해당 수직 간격에 도달할 때까지의 체공 시간 × 좌우 속도 90

이 불변식은 시드를 바꿔가며 테스트로 검증한다 (14절 참조).

## 6. 구간 (Zone)

| 구간 | 높이 | 배경 | 요소 |
|---|---|---|---|
| 땅 | 0 ~ 300m | 하늘색 → 연한 파랑 | 아래에 잔디, 구름 몇 개 |
| 하늘 | 300 ~ 900m | 파랑 → 보라 → 주황 노을 | 구름 많음, 새 |
| 우주 | 900m ~ | 남색 → 검정 | 별, 가끔 운석·행성 |

구간 경계에서 색이 급변하지 않도록 **높이에 따라 배경색을 선형 보간**한다.
구름은 위로 갈수록 옅어지고 별은 진해지며, 두 요소가 겹치는 전환 구간을 만들어
"어느새 우주에 와 있는" 느낌을 준다.

배경 요소(구름·별)는 **패럴랙스**로 카메라보다 느리게 움직여 깊이감을 만든다.

## 7. 에너지와 낙하

기본 최대 에너지 **3칸** (상점 업그레이드로 최대 5칸까지).

### 낙하 처리 순서

플레이어가 화면 하단 밖(`player.y < camera.y - 16`)으로 벗어나면 **아래 순서를
그대로 따른다.** 순서가 어긋나면 게임 오버인데도 구조 발판을 만들거나 부활 연출이
재생되는 낭비가 생긴다.

1. **무적 시간 중이면** 에너지도 방석도 소모하지 않고 **곧바로 부활**한다 (5단계로 이동)
2. **`run.cushionAvailable`이 참이면** 이를 거짓으로 바꾸고
   **에너지를 깎지 않은 채 부활**한다 (5단계로 이동)
3. 그렇지 않으면 **에너지 1칸 감소**
4. **에너지가 0이면 즉시 게임 오버하고 여기서 종료한다** — 부활 발판을 찾지도,
   구조 발판을 만들지도 않는다. 5단계로 가지 않는다
5. **부활 발판 위에 재배치**한다 (`vy = 0`, 좌우 속도 0). 무적은 **조건부로만**
   설정한다:
   - 현재 무적이 아니면 → `run.invulnerableUntil = now + 1.5초`
   - **이미 무적 중이면 → 기존 만료 시각을 그대로 유지한다** (연장 금지)

무적은 남은 시간이 아니라 **절대 만료 시각 `run.invulnerableUntil`로 저장**한다.
그래야 "이미 무적이면 건드리지 않는다"가 조건 한 줄로 끝나고, 재구조가 무적을
연장하는 사고가 구조적으로 불가능해진다.

재배치가 일어나는 지점은 **5단계 하나뿐**이다. 1·2단계는 재배치를 직접 하지 않고
5단계로 넘긴다.

### 방석은 재고가 아니라 "이번 판의 효과"를 소진한다

방석 재고는 **게임 시작 시 이미 1개 차감**되었다 (10절). 낙하 시점에 재고를 또
차감하면 **이중 차감**이다. 따라서 상태를 분리한다:

- 게임 시작 시: 재고 1 차감 → `run.cushionAvailable = true`
- 낙하 시: `run.cushionAvailable = false`로만 바꾸고 **재고는 건드리지 않는다**

### 무적 시간(1.5초)이 막는 것

이 게임에는 적도 공격도 없으므로, 무적이 실제로 막는 것은 **재낙하 하나뿐**이다.
그리고 이는 가정적 상황이 아니다 — 부활 발판은 `camera.y + 40` 이상, 낙하 판정선은
`camera.y - 16`이므로 최소 56px 낙하로 충분하고, 중력 1200에서
`t = √(2×56/1200) ≈ 0.31초`다. 발판 끝까지 걸어가는 시간을 더해도 1.5초 안에 다시
떨어질 수 있다.

규칙은 위 1단계 그대로다: **무적 중 낙하하면 에너지도 방석도 소비하지 않고 즉시
다시 구조한다.** 낙하 판정 자체를 무시하지는 않는다 — 그러면 플레이어가 화면 아래로
무한정 떨어지다가 무적이 끝나는 순간 죽는다.

**무적 타이머는 최초 부활 시점부터 흐르며, 재구조로 연장되지 않는다.** 연장하면
벽 쪽으로 계속 떨어지는 것만으로 무적을 무한히 유지할 수 있다.

### 부활 발판 선정

**부활 발판은 "마지막으로 착지했던 발판"이 아니다.** 다음 순서로 정한다:

1. **부활 후보 발판** 중 `y >= camera.y + 40`인 것들 가운데 **가장 낮은 발판**
2. 그런 발판이 없으면 `camera.y + 60` 높이에 **구조 발판을 생성**

**부활 후보 발판**은 다음을 모두 제외한 발판이다:

- 이미 소멸한 발판
- **소멸 타이머가 작동 중인 "부서짐" 발판** — 부활 직후 발밑이 사라진다
- **화면 밖으로 폐기 예정인 발판** — 부활하자마자 다시 낙하한다

후보가 하나도 없으면 그냥 구조 발판을 쓰면 되므로, 후보 조건은 얼마든지
엄격해도 안전하다.

### 왜 "마지막 착지 발판"이면 안 되는가

카메라는 내려가지 않고 화면 아래 발판은 폐기되므로, "마지막 착지 발판"은 부활
시점에 이미 화면 밖일 수 있다. 특히 **스프링 발판에서는 반드시 그렇게 된다** —
스프링은 234px을 올려보내고 카메라는 플레이어를 192px 아래에 두므로, 착지 시점에
스프링 발판은 이미 화면 하단보다 42px 아래다. 그 좌표에 부활시키면 화면 밖 →
즉시 재낙하 → 에너지 3칸이 한꺼번에 증발한다.

위 규칙은 부서진 발판 문제도 함께 해결한다. 규칙 하나로 두 문제를 처리한다.

**`run.maxHeight`와 `camera.y`는 부활해도 감소하지 않는다.** 잃는 것은 현재 물리
위치뿐이며, 점수와 진행도는 보존된다.

### 게임 오버

에너지가 0이 되면 게임 오버 → 결과 화면 → 로비.

**이번 판은 종료되지만 획득한 재화(실·코인)와 최고기록은 보존된다.**
`run.maxHeight`가 `save.bestHeight`를 넘었으면 기록을 갱신한다.

## 8. 아이템

### 드랍 확률

발판 생성 시 굴린다.

| 아이템 | 확률 | 효과 |
|---|---|---|
| 없음 | 82% | |
| 실 | 8% | 옷 제작 재료 |
| 코인 | 7% | 상점 재화 |
| 음식 | 2% | 에너지 +1 (가득 찬 상태면 코인으로 전환). **우주 구간에서는 나오지 않는다** |
| 물음표 | 1% | 퀴즈 발동 |

우주 구간에서는 실·코인이 한 번에 2~3개씩 드랍된다. 높이에 따라 위험이 커지는 만큼
보상도 커야 계속 올라갈 동기가 생긴다.

**우주에는 생명 유지 장치가 없다** — 음식 몫(2%)이 코인 2~3개로 바뀐다. 우주가 실·코인
2~3배에 회복까지 그대로면 순수 상향이라, 위험이 가장 큰 구간에 대가가 없다. 회복을 끊으면
"수입 2~3배 vs 회복 없음"이라는 거래가 성립한다.

주의할 점 둘:
- 이것은 **수입을 깎는 변경이 아니라 회복을 없애는 변경**이다. `grantFood`가 에너지 가득일
  때 이미 코인으로 바꿔주므로 성한 플레이어에게는 원래도 코인이었다. 실제로 손해를 보는 쪽은
  **이미 떨어져 본 플레이어**뿐이고, 그들에게 우주는 편도가 된다.
- 음식을 그냥 없애지 않고 코인으로 돌린다. 없애면 82%였던 "아이템 없음"이 84%가 되어 우주
  발판이 더 비어 보인다 — 보상을 키운다는 구간 설계와 어긋난다.

**퀴즈 보상의 에너지는 우주에서도 그대로다.** 회복 수단을 0으로 만들면 우주에서 한 번
다치는 순간 되돌릴 방법이 없어 좌절만 남는다. 1% 물음표가 우주의 유일한 회복원이 되면서
보상 선택 화면의 "에너지"가 처음으로 진짜 고민거리가 된다.

### 물음표 처리

물음표를 주우면 **게임을 일시정지**하고 퀴즈 모달을 띄운다. 단 **공중에서 주웠다면
착지할 때까지 미룬다** — 점프 도중에 모달이 뜨면 풀고 나왔을 때 플레이어가 공중
한복판에 놓여, 자기가 어디로 향하던 중이었는지 다시 파악해야 한다. 아이템은 닿는
즉시 사라지고 퀴즈만 발이 땅에 닿을 때 뜬다. 스프링처럼 착지와 동시에 다시 튕겨
나가는 경우는 아직 공중이므로 다음 착지까지 계속 기다린다.
들 수 있는 퀴즈는 하나뿐이라, 이미 하나를 들고 있으면 두 번째 물음표는 줍지 않고
발판에 남긴다. 들고 있는 채로 마지막 에너지를 잃으면 그 퀴즈는 판과 함께 사라진다.

정답이면 실/코인/음식 중 하나를 선택해 획득하고, 오답이면 아무것도 없다.
**오답에 에너지 페널티를 주지 않는다** — 1% 확률로 만난 보너스에서 벌을 주면
플레이어가 물음표를 피하게 된다.

### 일시정지 규약 (반드시 지킬 것)

일시정지는 "물리를 멈춘다"로 끝나지 않는다. 아래 네 규칙이 없으면 모달을 닫는
순간 시간이 순간이동하거나 의도치 않은 점프가 발생한다.

1. **퀴즈 중 물리 갱신과 게임 입력을 모두 정지한다.**
2. **퀴즈 제한시간(10초)은 실시간 기준으로 계속 흐른다** (`performance.now()`).
   물리를 멈춘 상태이므로 게임 시간에 연동하면 타이머가 얼어붙는다.
3. **모달 종료 시 고정 타임스텝 accumulator를 0으로 초기화한다.**
   초기화하지 않으면 모달이 떠 있던 시간만큼 물리 스텝이 한꺼번에 처리되어
   플레이어가 순간이동한다.
4. **모달 종료 시 키 입력 상태를 전부 "떼어짐"으로 초기화한다.**
   추가로 **점프는 `keydown` 엣지에서만 발동**하도록 규정한다. 그러면 모달에서
   정답 선택에 누른 Space가 게임 점프로 이어지는 문제가 구조적으로 사라진다
   (키가 눌린 채로 복귀해도, 다시 뗐다 눌러야 점프한다).

## 9. 옷 (실 소비)

옷은 **팔레트 + 선택적 장식 레이어**로 정의한다. 캐릭터 픽셀맵에서 `c`로 표시된 칸을
옷 팔레트 색으로 칠하고, 모자·헬멧·망토 등은 별도 픽셀맵을 위에 겹친다.
따라서 옷 한 벌 추가는 스프라이트 제작이 아니라 **데이터 몇 줄 추가**다.

| # | 옷 | 실 | 특징 |
|---|---|---|---|
| 1 | 기본 티셔츠 | 0 | 시작 시 지급 |
| 2 | 줄무늬 셔츠 | 5 | 2색 교차 |
| 3 | 노란 우비 | 12 | 모자 레이어 |
| 4 | 멜빵 청바지 | 22 | |
| 5 | 꽃무늬 원피스 | 35 | 치마 실루엣 변경 |
| 6 | 후드티 | 50 | 후드 레이어 |
| 7 | 마법사 로브 | 70 | 별 무늬 + 고깔모자 |
| 8 | 기사 갑옷 | 95 | 금속 음영 |
| 9 | 우주복 | 125 | 헬멧 + 산소통 |
| 10 | 은하 드레스 | 160 | 반짝임 애니메이션 |

**실은 제작 시 소모되지만, 제작한 옷은 영구 보유**하며 언제든 갈아입을 수 있다.

옷은 **순수 꾸미기 전용**으로 게임플레이 성능에 전혀 영향을 주지 않는다.
성능 성장은 상점이 전담하며, 두 시스템의 역할을 의도적으로 분리했다.

## 10. 상점 (코인 소비)

로비에서만 접근한다. 영구 업그레이드와 소모품으로 나뉜다.

### 영구 업그레이드

| 아이템 | 효과 | 가격 (레벨별) |
|---|---|---|
| 점프력 강화 | 점프 속도 +20/레벨 (480 → 540, 9.6m → 12m) | 30 / 70 / 150 |
| 에너지 확장 | 최대 에너지 3 → 4 → 5 | 100 / 250 |
| 공중 조향 | 좌우 속도 90 → 110 → 130 | 40 / 90 |
| 자석 | 아이템 자동 흡수 반경 0 → 20px → 40px | 60 / 140 |

### 소모품

1회용. 로비에서 구매해 재고로 쌓아두고, **판 시작 전 로드아웃 화면에서 명시적으로
장착**한다.

| 아이템 | 효과 | 가격 |
|---|---|---|
| 로켓 부츠 | 시작 지점을 100m로 올림 | 25 |
| 깃털 | 이번 판 중력 1200 → 900 px/s² (체공 시간 증가) | 15 |
| 방석 | 이번 판 **첫 낙하 1회**를 에너지 소모 없이 방어 (`run.cushionAvailable`) | 20 |
| 더블 점프 | 이번 판 내내 공중 점프 1회 사용 가능 (착지 시 재충전) | 35 |

### 소모품 규약

"판 시작 시 적용"만으로는 결정되지 않는 것들을 못 박는다.

| 질문 | 결정 |
|---|---|
| 자동 적용인가 장착인가 | **명시적 장착.** 자동 적용은 아까운 소모품을 낭비시킨다 |
| 동시 장착 개수 | **종류당 최대 1개**, 서로 다른 종류는 동시 장착 가능 (최대 4종) |
| 같은 종류 중첩 | **불가.** 깃털 2개를 써도 중력이 900 아래로 내려가지 않는다 |
| 차감 시점 | **게임 시작 직후, 첫 물리 프레임 이전에 차감하고 즉시 저장.** 새로고침으로 복제할 수 없다 |
| 게임 시작 실패 시 | 차감 전에 실패하면 재고 유지. 차감 후에는 환불하지 않는다 |

### 장착 목록과 재고의 동기화

`selectedConsumables`와 `consumables` 재고는 **따로 놀 수 있다.** 한 판에서 마지막
하나를 소진했는데 ID가 장착 목록에 남으면, 다음 판에 재고 0인 아이템이 장착된
상태가 되어 무료 적용이나 음수 재고로 이어진다.

게임 시작 시 다음을 하나의 원자적 단계로 처리한다:

1. `selectedConsumables` 중 **재고가 1개 이상인 항목만** 적용 대상으로 추린다
   (재고 0인 항목은 조용히 무시하고 목록에서도 제거)
2. 적용 대상만 재고에서 1씩 차감한다
3. 차감 결과 **재고가 0이 된 항목을 `selectedConsumables`에서 제거한다**
4. 재고와 장착 목록을 **함께 저장한다**
5. 차감한 소모품의 효과를 **이번 판 상태(`run.*`)에 반영한다**
   (예: 방석 → `run.cushionAvailable = true`, 더블 점프 → `run.doubleJump = true`)

**재고(`save.consumables`)와 이번 판 효과(`run.*`)는 별개다.** 재고는 시작 시 한 번만
차감되고, 판이 진행되는 동안 소진되는 것은 `run.*` 쪽이다. 이 구분을 지키지 않으면
방석처럼 판 중에 소비되는 아이템이 이중 차감된다 (7절 참조).

로드아웃 UI도 재고 0인 항목은 장착할 수 없게 막는다. 다만 UI 검사에만 의존하지
않고 위 시작 시점 검사를 반드시 둔다 — 저장 데이터가 손상된 경우에도 방어된다.

**더블 점프는 판 전체 1회가 아니라 착지할 때마다 재충전된다.** 35코인에 단 1회는
값어치가 없다. 즉 "이번 판 동안 항상 더블 점프가 가능한 상태"가 된다.

**로켓 부츠 처리:** 시작 시 `player.y = 1000px(100m)`에 놓고, 발판을 0~1000px
구간에 생성하지 않고 1000px부터 생성한다. `camera.y`와 `run.maxHeight`도 그에
맞춰 초기화한다. **`run.maxHeight`에 100m가 그대로 포함된다** — 대신 그 구간의
실·코인을 획득할 기회를 통째로 포기하므로 자체적으로 균형이 맞는다.

가격대가 15부터 250까지 분포하므로, 코인이 적을 때는 소모품으로 한 판을 버티고
모이면 영구 업그레이드로 넘어가는 자연스러운 흐름이 생긴다.

## 11. 퀴즈

문제는 `src/data/quiz.json`으로 **완전히 분리**한다. 코드 수정 없이 문제를
추가·교체할 수 있다.

- 초기 **40문항**, easy / normal / hard 난이도 분류
- 4지선다, **제한시간 10초**
- **물음표 아이템이 놓인 발판의 높이**에 따라 난이도를 선택해 출제
  (3절의 원칙대로, 생성 시점에 결정되는 값은 발판 자신의 y를 쓴다)

### 보상 (정답 시 3종 중 택 1)

| 난이도 | 실 | 코인 | 음식 |
|---|---|---|---|
| easy | 3 | 3 | +1 |
| normal | 6 | 6 | +1 |
| hard | 12 | 12 | +1 |

출제된 문제 ID를 저장해 반복 출제를 막고, 해당 난이도의 문제 풀이 소진되면
그 난이도의 이력만 초기화한다.

## 12. 저장

`localStorage` 단일 키 **`life-jump-save-v1`**.

```ts
interface SaveData {
  version: number            // 스키마 마이그레이션용
  bestHeight: number         // 최고 기록 (px) — 표시할 때만 PX_PER_M로 나눈다
  totalRuns: number
  thread: number             // 보유 실
  coins: number              // 보유 코인
  ownedOutfits: string[]     // 제작 완료한 옷 ID
  equippedOutfit: string     // 착용 중인 옷 ID
  upgrades: {
    jump: number             // 0-3
    energy: number           // 0-2
    air: number              // 0-2
    magnet: number           // 0-2
  }
  consumables: {              // 보유 재고
    rocket: number
    feather: number
    cushion: number
    doubleJump: number
  }
  selectedConsumables: string[]   // 다음 판에 장착할 종류 (종류당 1개, 최대 4)
  seenQuizIds: string[]
}
```

### 로드 파이프라인

**필드가 몇 개 빠졌다고 전체를 초기화하면 플레이어 진행도가 통째로 날아간다.**
따라서 "파싱 실패 → 전체 리셋"이 아니라 다음 5단계를 거친다.

1. **파싱** — `JSON.parse` 실패 시에만 전체 기본값으로 시작
2. **버전별 마이그레이션** — `version`을 보고 순차 변환 (v1 → v2 → …)
3. **기본값과 깊은 병합** — 누락된 필드만 기본값으로 채운다. 존재하는 값은 보존
4. **유효성 검증 및 보정** — 숫자 범위 클램프(음수 재화 → 0, 업그레이드 레벨 초과
   → 최대치), 알 수 없는 옷/상점 ID 제거, `equippedOutfit`이 `ownedOutfits`에
   없으면 기본 티셔츠로 교체
5. **복구 결과 재저장** — 보정된 데이터를 즉시 다시 저장해 다음 로드를 깨끗하게 한다

저장 데이터가 손상됐다고 게임이 켜지지 않아서는 안 되며, 동시에 **복구 가능한
손상을 전체 초기화로 처리해서도 안 된다.**

## 13. 아키텍처

### 핵심 원칙

**`game/` 아래의 어떤 파일도 `render/`를 import하지 않는다.**

게임 로직을 렌더링에서 완전히 분리하면 (1) 로직을 순수 함수로 테스트할 수 있고,
(2) 향후 렌더러 교체가 `render/` 디렉토리 교체로 끝난다.

### 파일 구조

```
src/
  main.ts               진입점, 씬 전환 (로비 ↔ 게임)

  core/
    loop.ts             고정 타임스텝 루프
    input.ts            키보드·터치 소스 상태 추적 (OR 합산)
    touch.ts            Pointer Events → 존/조이스틱 판정 (터치 스펙 4절)
    rng.ts              시드 가능한 난수 (테스트 재현성)
    storage.ts          저장/로드 + 마이그레이션 + 손상 복구

  game/                 ← 렌더링을 전혀 모르는 순수 로직
    state.ts            GameState 타입, 초기화
    physics.ts          중력, 이동, 스윕 충돌
    platforms.ts        발판 생성·재활용·종류 결정
    items.ts            드랍 굴림, 획득 처리
    zones.ts            높이 → 구간 판정 + 배경색 보간
    update.ts           한 틱 전체 업데이트 (위 조각들 조립)

  render/
    canvas.ts           정수 배율 스케일링, 레터박스
    sprites.ts          픽셀맵 → 오프스크린 캔버스 캐시
    drawGame.ts         월드 렌더링 (배경, 발판, 아이템, 플레이어)
    drawHud.ts          에너지·높이·재화 표시

  data/
    pixelmaps.ts        캐릭터·발판·아이템 픽셀맵
    outfits.ts          옷 10벌 정의
    shop.ts             상점 8종 정의 (영구 4 + 소모품 4)
    quiz.json           퀴즈 40문항

  ui/                   ← DOM 기반
    lobby.ts            로비 화면
    wardrobe.ts         옷장
    shop.ts             상점
    loadout.ts          판 시작 전 소모품 장착 화면
    quizModal.ts        퀴즈 모달
    touchOverlay.ts / touchHint.ts   터치 글리프·첫 판 안내
    styles.css

  toss/
    screen.ts           앱인토스 SDK 래퍼 (스와이프백)
```

로비·상점·옷장·퀴즈 UI를 캔버스가 아니라 **DOM**으로 만든다. 버튼, 스크롤, 호버,
접근성이 전부 공짜로 따라온다. 캔버스 안에 UI를 직접 그리는 것은 비용이 크다.

### 픽셀맵 표현

스프라이트는 문자열 배열 + 팔레트 맵으로 소스에 정의한다.

```ts
const BODY = [
  '....hhhh....',   // h = 머리카락
  '...hssssh...',   // s = 피부
  '...hs.s.s...',   // c = 옷  ← 팔레트로 교체
  '....ssss....',
  '...cccccc...',
  '..c.cccc.c..',
  '....cccc....',
]
```

### 스프라이트 캐싱

픽셀맵을 매 프레임 픽셀 단위로 그리면 느리다. 시작 시 각 스프라이트(옷 조합 포함)를
**오프스크린 캔버스에 한 번만 렌더링**해두고, 매 프레임에는 그 캔버스를
`drawImage`로 통째로 복사한다. 착용 옷이 바뀔 때만 캐시를 재생성한다.

## 14. 테스트 전략

Vitest. 렌더링·DOM은 테스트하지 않는다 (비용 대비 가치 낮음). 대신 순수 함수
단위 테스트와, 상태 규칙이 얽히는 지점의 통합 테스트를 함께 둔다.

### 단위 테스트 (순수 함수)

| 대상 | 검증 내용 |
|---|---|
| `physics` | 고속 낙하(600px/s)에서 발판을 관통하지 않는가 — 스윕 충돌의 존재 이유 |
| `physics` | 가변 점프 컷오프가 최소 3.7m / 최대 9.6m 경계를 지키는가 |
| `platforms` | **생성된 모든 발판이 직전 발판에서 도달 가능한가** — 시드를 바꿔가며 수천 회 검증 |
| `platforms` | 이동 발판이 끼었을 때 **최악 위치 조합**에서도 도달 가능한가 |
| `zones` | 구간 경계에서 배경색 보간이 연속인가 |
| `storage` | 필드가 일부 누락된 저장을 **전체 초기화 없이** 병합 복구하는가 |
| `storage` | 파싱 불가 문자열, 음수 재화, 범위 초과 업그레이드 레벨을 보정하는가 |

### 드랍 확률 테스트 — 두 종류로 분리한다

표본 분포가 명세와 "정확히 일치"하는지 검사하면 **간헐적으로 실패(flaky)한다.**
난수는 표본마다 흔들리기 때문이다. 그래서 두 층으로 나눈다:

1. **경계 매핑 테스트 (결정론적)** — 난수 값을 직접 주입해 확률 구간 경계가 올바른
   아이템으로 매핑되는지 검사한다. `0.82` 직전/직후, `0.90`, `0.97`, `0.99` 등
   각 구간 경계값에서. 이 테스트는 절대 흔들리지 않는다.
2. **통계 테스트 (넓은 허용오차)** — 고정 시드로 10만 회 굴려 각 아이템 빈도가
   명세 ±20% 안에 있는지만 본다. 분포가 통째로 잘못된 경우만 잡는 안전망이다.

### 통합 테스트 (규칙이 얽히는 지점)

단위 테스트로는 잡히지 않고, 실제로 게임을 망가뜨렸던 상호작용들이다.

| 시나리오 | 기대 결과 |
|---|---|
| 스프링 점프 후 추락·부활 | 부활 직후 플레이어가 **화면 안**에 있고, 즉시 재낙하하지 않는다 |
| 마지막 착지 발판이 "부서짐"으로 소멸한 뒤 추락 | 정상 부활한다 (살아있는 발판만 후보) |
| 소멸 타이머가 돌고 있는 부서짐 발판만 화면에 남은 상태에서 추락 | 그 발판을 고르지 않고 **구조 발판을 생성**한다 |
| 퀴즈 모달을 5초간 띄웠다가 닫음 | 시간 점프가 없고(accumulator 초기화), 점프가 발동하지 않는다 |
| 탭을 30초간 백그라운드에 두었다 복귀 | 밀린 시간을 따라잡는 슬로모션이 발생하지 않는다 |
| 소모품 장착 후 게임 시작 | 재고가 **정확히 1개만** 차감된다 |
| 소모품 차감 직후 새로고침 | 재고가 복원되지 않는다 (복제 불가) |
| 마지막 남은 소모품을 사용해 재고가 0이 됨 | `selectedConsumables`에서 해당 ID가 **제거된 채로 저장**된다 |
| 재고 0인 ID가 `selectedConsumables`에 남아 있는 손상된 저장으로 시작 | 적용되지 않고 음수 재고도 생기지 않는다 |
| 에너지 1칸 + 방석 장착 상태에서 낙하 | 게임 오버 없음. **방석 효과(`run.cushionAvailable`)만 소진**되고 에너지와 **재고는 그대로**다 |
| 방석을 소진한 뒤 판 종료 | 재고가 **시작 시 1회만** 차감되어 있다 (이중 차감 없음) |
| 에너지 1칸 + 방석 없이 낙하 | **즉시 게임 오버.** 구조 발판을 생성하지 않고 부활 연출도 없다 |
| 무적 시간(1.5초) 중에 다시 화면 밖으로 낙하 | 에너지·방석을 소비하지 않고 즉시 재구조된다 |
| 무적 중 재구조를 3회 반복 | 무적 타이머가 **연장되지 않고** 최초 부활 시점부터 1.5초 뒤 종료된다 |
| 이동 발판이 포함된 구간을 실제로 시뮬레이션 | 생성기가 승인한 배치가 실제 물리에서도 도달 가능하다 |

마지막 항목은 5절의 정적 불변식이 **보수적으로 옳은지**를 실제 물리로 교차 검증하는
테스트다. 생성기와 물리가 서로 다른 가정을 갖게 되는 것을 막는다.

발판 도달 가능성은 간격 랜덤화 때문에 **언젠가 반드시 깨질 불변식**이므로,
`rng.ts`의 시드 기능을 활용해 광범위하게 검증한다.
